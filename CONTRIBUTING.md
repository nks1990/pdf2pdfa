# Contributing

Thank you for improving `pdf2pdfa`.

The project handles an archival format where a plausible-looking output is not enough. Version 5 adds an equally strong architectural constraint: **runtime PDF functionality must be implemented and reviewable in this repository rather than delegated to an external PDF/validation/rendering library or executable.**

## Development setup

```bash
python -m venv .venv
# activate the environment for your platform
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
python scripts/check.py
```

There is intentionally no push/pull-request CI workflow. Contributors are responsible for running the relevant manual gate before opening or merging a change.

Before release-level changes:

```bash
python scripts/check.py --full
```

The full gate is self-contained with respect to PDF processing: it exercises the owned parser, repair engine, validator, renderer/fidelity stack and 1b/2b/3b smoke conversions.

## Runtime ownership rule

Do not add a runtime dependency as a shortcut for a missing PDF feature.

Examples of changes that are **not** acceptable for the v5 runtime architecture:

- calling a system PDF converter/validator/rasterizer;
- importing a third-party PDF parser/writer;
- importing an image library merely to decode a PDF image codec;
- importing a font library merely to parse/render PDF fonts;
- adding a validation service/API call;
- bundling copied binary assets when the required archival data can reasonably be generated/implemented in owned source.

If a feature is too large to implement safely in one change, leave the path explicitly unsupported and implement it incrementally with tests. Unsupported is better than hidden delegation or guessed output.

Build/test tooling is separate from runtime. pytest/setuptools/build/twine may be used for development and packaging, but code under `pdf2pdfa/` must satisfy the ownership tests.

## Pull-request expectations

A change should normally include:

- a focused explanation of the PDF/PDF-A behavior being changed;
- regression tests for both valid and malformed/adversarial forms where appropriate;
- no silent weakening of validator, repair or fidelity policy;
- documentation changes when public behavior/coverage changes;
- an explicit note for fidelity, security or compatibility tradeoffs;
- the manual check command(s) run;
- for new runtime modules, confirmation that ownership/module-graph tests pass.

## Fixtures

Prefer small PDFs generated by `pdf2pdfa.native.builder.PDFBuilder` directly in `tests/native` or `tests/owned`. A reviewer should be able to see the exact objects/content stream that create the test condition.

A binary fixture is justified only when the bug depends on a real producer or malformed byte layout that cannot be reproduced faithfully with a concise generator. Before adding one:

1. remove private/identifying content;
2. minimize the file;
3. document origin and redistribution permission;
4. explain the exact regression;
5. avoid using the fixture as an unexplained pass/fail oracle.

Never add confidential documents.

## Parser/writer changes

Parser correctness is upstream of every conformance decision.

Changes to tokenizer/xref/object-stream/stream-length/resolution logic should include:

- a byte-level success case;
- a malformed/truncated case;
- bounds/cycle behavior when applicable;
- write/reparse coverage when the change affects serialization.

Do not make repair mode permissive in a way that changes strict parsing/validation into silent acceptance.

## Conformance changes

Do not add support for a PDF/A feature by changing only metadata or by suppressing a failing rule.

A rule/feature change normally needs:

1. explicit policy/rule logic;
2. positive and negative fixtures;
3. structured failure id/path assertions;
4. a repair only if semantics can be proven safe;
5. post-repair reparse + owned validation;
6. fidelity coverage if painting or document semantics can change;
7. documentation of coverage/limitations.

Because the validator is owned, a newly discovered standards edge case is our implementation work. Do not work around it by calling another validator.

## Repair changes

A repair must correspond to a known validation failure and must not mutate unrelated structure.

If a repair changes page painting, it belongs behind visual fidelity in default `auto` mode. If it changes only structural/archival metadata, semantic fidelity should remain stable except for explicitly permitted fields.

Block an ambiguous case rather than broadening the repair until it happens to validate.

## Fidelity changes

Semantic and visual fidelity serve different changes.

- structural repair: semantic fingerprinting;
- intentional painting rewrite: owned visual renderer comparison.

Do not loosen thresholds just to pass a regression. Explain any threshold change quantitatively and add a fixture demonstrating why the previous threshold was wrong.

A renderer enhancement should have direct renderer tests plus fidelity/flattening tests when relevant.

## Font changes

Never guess a complex character-code-to-glyph mapping or select a system look-alike font.

Font work should preserve the chain:

PDF character code → Encoding/CMap → CID/glyph id → embedded/explicit font program → glyph outline/metrics.

Explicit unsupported cases (for example an outline/CMap form not yet implemented) should remain blockers until an owned parser/interpreter is available.

Check embedding permissions before embedding supplied fonts.

## Image/codec changes

New image decoders are security-sensitive binary parsers. Include:

- minimal valid streams;
- truncation/malformed tables;
- dimension/resource limits;
- color/decode handling;
- renderer integration;
- visual comparison where the decoder affects flattening.

Do not use an OS/image package fallback for JPX/JBIG2/CCITT or future codecs.

## Transparency changes

Transparency correctness depends on backdrop/group semantics, not just alpha multiplication. Changes to blend modes, soft masks, isolated/non-isolated groups or knockout groups need small pixel-expected tests.

If semantics are not complete, keep the group type unsupported for flattening instead of approximating it.

## Security-sensitive changes

Do not put passwords/secrets in command-line arguments, logs, exceptions or test snapshots. Preserve bounds checking and atomic publication.

Signed documents must remain opt-in for destructive rewrite. The project does not validate signature trust/chains.

## Public API compatibility

Correctness and ownership take precedence over preserving an old API that exposes removed architectural concepts. Version 5 intentionally removes backend and external-validator selection.

New public API should describe user intent (`level`, `fidelity`, font input, security policy), not implementation escape hatches.

Breaking changes require an appropriate major version and changelog/migration documentation.

## Before merging

At minimum run the most relevant tests. For broad engine/API changes run:

```bash
python scripts/check.py --full
```

Also verify:

- `dependencies = []` remains true;
- `tests/owned/test_package_ownership.py` passes;
- no push/PR workflow was added;
- unsupported-feature documentation still matches actual fail-closed paths.
