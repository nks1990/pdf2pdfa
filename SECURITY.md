# Security policy

## Supported versions

Security fixes are applied to the current supported major release. Upgrade to the latest release before reporting a suspected vulnerability as unresolved.

## Reporting a vulnerability

Do not publish exploit details in a public issue before maintainers have had a reasonable opportunity to investigate. Use GitHub's private vulnerability reporting feature for this repository when available.

A useful report includes:

- affected `pdf2pdfa` version or commit;
- operating system and Python version;
- the smallest reproducible PDF or generated byte sequence;
- expected versus observed behavior;
- whether the issue permits code execution, arbitrary file access, secret disclosure, denial of service, validator bypass or document corruption;
- the parser/rule/renderer path involved when known.

Do not include real passwords, private keys, confidential PDFs or other secrets.

## Threat model

PDF input is attacker-controlled structured binary data. The owned engine therefore treats every length, count, offset, nesting level, compressed stream and lookup table as untrusted.

The security boundary is simpler in v5 because conversion does not invoke an external PDF process or third-party PDF/image/font runtime library. That removes subprocess-command construction and external-engine patch level from the normal runtime threat surface, but it also means parser/codec/security correctness is directly our responsibility.

## Password handling

Encrypted input accepts a password through the Python API, `--password-file`, or `PDF2PDFA_PASSWORD`. There is intentionally no plaintext `--password TEXT` CLI option because process arguments can be visible to other local processes or telemetry.

Authentication and decryption are performed by `pdf2pdfa.native.security` and `pdf2pdfa.native.aes` in-process. A plaintext working document is kept in Python-managed memory/object structures and temporary candidate files as needed; no password is passed to another executable.

Do not include passwords in exception messages, logging, snapshots or fixtures.

## Parser and decoder safety

Owned parsing/decoding code must be bounded and fail closed.

Security-sensitive areas include:

- xref and object-stream offsets;
- indirect `/Length` values;
- deeply nested arrays/dictionaries;
- decompression expansion;
- LZW/predictor dimensions;
- image width/height/component multiplication;
- ICC tag offsets and table counts;
- TrueType/CFF table offsets and glyph counts;
- CMap code ranges;
- recursive Form XObjects, masks and resource graphs;
- page-tree and name-tree cycles;
- encryption revision/key-length fields.

New code in these areas should validate arithmetic bounds before allocation/iteration and include malformed-input regression tests.

## Resource exhaustion

`max_input_bytes` / `--max-input-mib` can reject large files before parsing, but file size alone is not a complete denial-of-service defense. Small PDFs can contain highly compressed streams, huge page/image dimensions, cyclic structures or expensive content.

Library-level safeguards should bound recursion, decoded sizes and suspicious counts. Applications that accept hostile uploads should additionally apply process/container CPU, memory, wall-clock and filesystem quotas.

The package is a parser/converter, not an OS sandbox.

## Atomic output

All rewrites produce a private candidate and publish with `os.replace` only after owned validation and the selected fidelity gate pass. A parsing, password, repair, validation or fidelity failure must preserve any pre-existing destination.

Any new write path must preserve this invariant.

## Digital signatures

A cryptographic PDF signature covers byte ranges. Any rewrite can invalidate those ranges even when the visible document is unchanged.

Applied signatures are refused by default. Empty signature fields are not treated as applied signatures. Signature invalidation requires explicit opt-in.

`pdf2pdfa` detects signature presence for rewrite safety; it is not a cryptographic signature verifier or trust-chain validator.

## Active content

PDF/A conversion identifies/removes profile-incompatible active actions only where the archival transformation is understood. This should not be confused with malware analysis.

The project is not:

- an antivirus scanner;
- a malware sandbox;
- a JavaScript behavior analyzer;
- a general-purpose hostile-PDF sanitizer;
- a redaction tool.

A PDF/A-valid result is an archival conformance result under the owned rule engine, not a security-clean bill of health.

## Rendering safety

The visual-fidelity/PDF/A-1 flattening renderer interprets untrusted painting instructions. Unsupported operators/resources must raise rather than falling through to arbitrary behavior.

Image dimensions, recursion into Form XObjects/masks and path complexity should remain bounded. A newly implemented codec must include malformed/truncated-data tests before being used by the page renderer.

## Font safety

Font programs are binary parsers too. Explicit font input and embedded fonts are untrusted. Table directories, offsets, glyph programs, contours, composites and CMap ranges must be bounds-checked.

The engine must not execute font-supplied native code; supported font data is interpreted by repository-owned parsers.

## Temporary files

Temporary candidate directories are created with Python's temporary-directory facilities, preferably on the destination filesystem so final replacement is atomic.

Applications with strong confidentiality requirements should use encrypted storage and platform-appropriate access controls for temporary and destination directories. Avoid placing password files in shared-readable locations.

## Dependency and supply-chain policy

The installed runtime declares zero third-party dependencies. `tests/owned/test_package_ownership.py` guards that architecture.

Development/build tools such as pytest, setuptools, build and twine are not imported by the runtime package. They should still be obtained from trusted package sources and kept current for development/release work.

The only GitHub workflow should remain the tag-triggered publication workflow; ordinary pushes and pull requests intentionally do not execute Actions.

## Security changes checklist

For security-sensitive changes:

1. add a minimal malformed/adversarial regression test;
2. verify failure is bounded and deterministic;
3. verify destination atomicity where conversion is involved;
4. avoid weakening fail-closed behavior to support a malformed file;
5. run `python scripts/check.py --full` manually;
6. document any newly supported parser/codec/security revision and its limits.
