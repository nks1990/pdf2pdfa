# Testing

The v5 test strategy proves three separate things: the owned PDF engine behaves correctly, the owned PDF/A rule engine rejects/accepts the intended structures, and conversion preserves document semantics or appearance according to the repair performed.

The repository intentionally has no push/pull-request CI workflow. Quality gates are run manually before merging and releasing.

## Fast quality gate

```bash
python -m pip install -e ".[dev]"
python scripts/check.py
```

This runs the release-layout/ownership sanity check and the complete canonical pytest suite under `tests/native` and `tests/owned`.

## Package gate

```bash
python scripts/check.py --package
```

This also rebuilds wheel/sdist from scratch and runs `twine check`. Package metadata is expected to declare zero runtime dependencies.

## Full owned gate

```bash
python scripts/check.py --full
```

The full gate adds an end-to-end smoke run for PDF/A-1b, 2b and 3b using only repository-owned runtime code. The 1b case deliberately includes transparency so the owned renderer/flattening/visual-fidelity path is exercised rather than only metadata normalization.

No external PDF converter, validator or rasterizer is required by the full gate.

## 1. Parser and writer tests

These tests cover the structures that determine whether every later decision is trustworthy:

- lexical names, strings, arrays, dictionaries and references;
- classic xref tables;
- xref streams;
- object streams;
- incremental `/Prev` chains;
- malformed-xref repair mode;
- stream boundaries and indirect `/Length`;
- reachable object walking;
- deterministic writer output and reparsing.

Every parser bug that can be minimized should become a byte-level regression fixture generated by owned code.

## 2. Stream/filter tests

The owned filter suite covers supported PDF filters and predictors, including malformed/truncated inputs and decompression limits. A codec that is not implemented must raise an explicit unsupported/error path rather than return guessed bytes.

Terminal image codecs are tested separately from general stream filters.

## 3. Security tests

Security-handler tests cover supported Standard Security Handler revisions, user/owner passwords, wrong/missing passwords, object-key derivation, RC4/AES primitives and removal of encryption before archival output.

Security tests must also verify:

- passwords never appear in logs/errors intended for users;
- applied signatures are distinguished from empty signature fields;
- signed input is refused unless invalidation was explicitly allowed;
- a failed password or security operation never overwrites an existing destination.

## 4. PDF/A rule-engine tests

`tests/native` generates targeted PDF structures using the owned `PDFBuilder`. Rules are tested at the level where they are enforced:

- header/version/xref restrictions;
- encryption and forbidden filters;
- XMP/PDF-A identification;
- JavaScript/actions;
- annotations and appearance resources;
- forms;
- font embedding/use;
- device/ICC color and OutputIntent;
- embedded/associated files;
- optional content;
- PDF/A-1 transparency;
- profile differences among 1b/2b/3b.

A conformance regression should assert the exact `rule_id` and, where meaningful, object/path reported by the validator.

## 5. Repair tests

Every repair rule needs three kinds of test when applicable:

1. the planner recognizes a repairable validation failure;
2. the repair changes only the intended structure;
3. the rewritten candidate reparses and passes the owned validator.

Unsupported or ambiguous structures need blocker tests as well. The correct result for an unimplemented transformation is a predictable failure, not a weaker validation rule.

## 6. Rendering tests

Rendering is product code because visual fidelity and PDF/A-1 transparency repair depend on it.

Component tests cover:

- matrix/path geometry;
- clipping and filling;
- affine-correct strokes;
- device and ICC color;
- image sampling/masks/soft masks;
- baseline JPEG;
- text state and supported TrueType/CID text;
- opacity and blend modes;
- soft masks and supported transparency groups;
- page rotation and crop geometry.

When a newly supported PDF painting primitive is added, include both a direct renderer test and a visual-fidelity/flattening test if that primitive can appear on pages requiring rewrite.

## 7. Fidelity tests

### Semantic fidelity

For structural repairs, compare stable document semantics such as page geometry, decoded painting content, text-show instructions, images and attachment inventory. Tests should explicitly whitelist only changes permitted by the repair plan.

### Visual fidelity

When painting is intentionally rewritten, render source and candidate through the same owned engine and compare RGB output in memory. Tests cover page count, page geometry, pixel tolerance, mean error and changed-pixel ratio.

Do not weaken tolerances merely to make a regression pass. If a tolerance changes, document the numerical/renderer reason.

## 8. Ownership tests

`tests/owned/test_package_ownership.py` is a release invariant, not a style test. It verifies:

- every distributed runtime import is stdlib or `pdf2pdfa`;
- every distributed Python module imports successfully;
- `pyproject.toml` keeps `dependencies = []`;
- old external-engine tokens/imports do not reappear in package source.

`tests/native/test_native_module_graph.py` separately verifies that relative imports inside the native engine point to real repository modules. This prevents a branch integration from producing a package that refers to a missing internal component.

## 9. Public API and CLI tests

Test through `from pdf2pdfa import Converter`, not only internal classes. Public tests cover:

- `inspect` repair-plan output;
- `validate` structured owned reports;
- successful conversion and mandatory validation;
- JSON CLI output;
- batch exit behavior;
- removed backend/validator options remaining unavailable;
- atomic destination preservation on failure.

## Generated versus real-world corpus

Generated fixtures are preferred because they are auditable down to the object dictionary that creates the condition.

Some bugs depend on producer-specific or malformed byte layouts. In those cases a minimized binary fixture is acceptable only when redistribution is permitted and provenance is documented. Never commit confidential documents.

Useful producer classes for a long-term corpus include office suites, browsers, CAD/GIS software, scanners/OCR tools, signed forms, CJK/CID documents and mixed print-color documents.

A real-world fixture must not become an opaque oracle: its expected rule/repair behavior should be documented in the test.

## Fuzz/property direction

The parser, filter decoders, CMap/font parsers, ICC parser and content parser are good candidates for deterministic mutation/property testing. Useful invariants include:

- parse → write → parse preserves reachable structure;
- malformed lengths/counts fail within configured bounds;
- decoders never read beyond input/table bounds;
- writer output can always be reparsed by the owned parser;
- validator never reports compliant after an internal parse/classification failure relevant to PDF/A.

## Cross-platform manual smoke testing

Before a significant release, exercise at least one supported Python on Windows, macOS and Linux when practical. Platform-sensitive areas are now mostly filesystem semantics, atomic replacement, path handling, temporary directories and Python-version behavior—not discovery of external executables.

## Before release

A release candidate should satisfy all of the following:

1. `python scripts/check.py --full` passes;
2. wheel/sdist build and pass `twine check`;
3. `python scripts/release_check.py` passes;
4. `pyproject.toml` declares zero runtime dependencies;
5. ownership and module-graph tests pass;
6. no known unsupported rendering/codec path is mislabeled as supported;
7. README/compliance limitations match current engine coverage;
8. no known regression is hidden by an unjustified skip;
9. `.github/workflows/` contains only the tag-triggered release workflow;
10. the release tag equals `v<project.version>`.
